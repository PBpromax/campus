# 第五步：确认后执行真实任务

本步基于四业务草稿与 DeepSeek 流式对话，接通原任务服务的发布、接单和取消。本机日期 2026-10-24，数据库为隔离的 `campus_m2_dev`。这是真实的本地数据库操作，验证数据均为明确标记的测试委托，不代表有人完成了真实校园服务。

## 操作路径

> 对话澄清 → 采用字段建议／自己补充 → 保存并确认草稿 → 补充发布资料 → 准备执行确认卡 → 核对服务端内容 → 明确确认执行 → 查询回执和审计。

AI 新增 `suggest_action`，只能建议 `PUBLISH / ACCEPT / CANCEL`。服务端核对用户本轮原话中是否有相应操作表达、任务编号是否明确出现，拒绝未知动作和额外参数。该有限检查不等于完备的语义判断；建议仍须人审核。AI 流处理器没有调用执行服务，不能创建任务、接单或取消。

鸿蒙“核对这条建议”只填入待操作类型／任务编号。没有模型建议时，也能使用同一固定操作入口。准备和执行是两个按钮，两次独立请求。普通学习答疑仍不要求报酬、地点和截止时间。

## 发布、接单与取消

发布只接受本人当前业务已补齐且已确认的草稿。服务端生成完整描述，不能由模型改写类别或遗漏借还／交接约定。原任务描述最多 500 字，超出即要求缩短并重新确认，不自动截断。用户另外明确填写标题、正数报酬、地点和未来完成时间，系统不擅自补值。

四业务都走原统一任务状态机：`PENDING → IN_PROGRESS → PENDING_CONFIRMATION → COMPLETED`，另有 `CANCELLED`。OTHER 多人意向仅支持一人协调；明确要求拆成多任务时拒绝一次发布，不能冒充已经创建多人接单能力。

接单需要明确任务编号、非本人发布、仍待接单且满足原信用规则。列表提供最近最多 20 条可接任务／本人任务，只返回摘要。准备后任务发生变化，执行会要求重新核对。

取消沿用原规则：发布方只可取消未被接单且仍在原取消窗口的任务；接单方取消进行中或待确认任务必须填写理由，扣 5 分信用。窗口继续使用原服务的整数分钟计算，未在本步重新定义。确认卡会显示这些后果。支付的 `HELD / REFUNDED / RELEASED` 仅为业务字段，未接入真实扣款、托管或退款。

## 持久化回执、幂等与事务

新增 `tool_intents` 保存待执行内容、预览、来源版本、有效期和结果；`tool_audits` 保存准备、成功、拒绝、撤回及失败记录。

- 同一用户与 `requestKey` 唯一：相同合法内容再次准备返回原请求；内容不同返回 409。
- 待执行卡有效期 5 分钟，绑定来源会话版本／草稿版本或任务行版本。修改、切换、过期和状态变化均需重新核对。
- 同一版本草稿只可成功发布一次，即使换一个请求编号也不能重复发布；修改后产生的新草稿版本仍需重新确认。
- 成功请求再执行，返回数据库内保存的原回执，不再次写任务、发通知或扣信用；后端进程重启后仍有效。
- 请求超时或执行结果不明时先查询原回执，客户端不自动重发或另建请求。成功回执是执行时的历史结果，当前任务状态应刷新任务列表查看。
- 执行时锁定用户、待执行请求及相关任务／草稿，任务和用户另加乐观版本。业务写入、通知、成功回执及成功审计在同一事务中提交。
- 通知等内部步骤失败时整个业务事务回滚；失败记录在回滚后的独立事务保存。数据库整体不可用时，不能保证失败审计也写成功。当前没有真实外部支付，因此没有实现外部退款补偿或分布式事务。

撤销待执行卡只会把请求变为 `REVOKED`，不会取消已发布任务。取消已发布任务必须重新选择 `CANCEL`，准备并确认。

## 接口与权限边界

以下接口均在 `/api/trusted-tools` 下，使用平台 JWT，账号来自服务端认证上下文，不接受模型指定操作人。

| 方法及路径 | 用途 |
| --- | --- |
| POST `/prepare` | 校验来源及参数，生成待执行确认卡 |
| POST `/{id}/execute` | 正文必须为 `{ "confirmed": true }`，再次校验后执行 |
| POST `/{id}/revoke` | 撤回本人尚未执行的请求 |
| GET `/{id}` | 读取本人回执，其他用户访问为 404 |
| GET `/` | 本人最近 20 份回执 |
| GET `/audits` | 本人最近 50 条审计 |
| GET `/tasks?scope=available` 或 `mine` | 读取操作所需任务摘要 |

原 Vue／任务 API 保留兼容，新增行版本保护也覆盖其并发写入；**旧路由并未全部迁入确认网关与统一审计**。因此本步保证的是鸿蒙新入口及新增 AI 操作链路，不宣称所有旧接口都已获得同样的确认、幂等和审计能力。模型只接触建议函数，不拿到平台 JWT，也不直接访问旧写接口。

## 部署与复核

先确认目标数据库并备份，再执行 `database/migrations/003_trusted_tools.sql`。它为用户／任务增加行版本，并创建两张工具表；本机已重复执行两次验证，不删除旧数据。之后运行 `python3 scripts/dev-backend.py`，构建并安装最新主 HAP 和测试 HAP。具体环境命令见 `harmony/README.md`。

常规验证不调用模型：

```sh
# 仓库根目录，需 Java 21
mvn -f backend/pom.xml -B -Dspring.profiles.active=test test

# 主包、测试包装好且后端／hdc 转发正常后
hdc -t 127.0.0.1:5555 shell aa test -b com.pbpromax.campus -m entry_test -s unittest OpenHarmonyTestRunner -w 60
```

真实 MySQL 脚本需分两阶段：

```sh
python3 scripts/verify-trusted-tools.py seed
# 停止本人后端，确认8081空闲，重新启动后
python3 scripts/verify-trusted-tools.py verify
```

只有显式添加 `seed --live-action` 才做一次付费 DeepSeek 请求，无自动重试。默认私有状态在 `/tmp/campus-step5-private-state.json`，权限600；存在时不重复 seed。测试审计及明确标记的委托保留供复核，不清库；不要指向真实用户数据库。

## 实际结果与下一步

后端 237 项、模拟器 Hypium 27 项通过。新增测试覆盖四业务发布、权限、过期／修改失效、幂等、撤回、并发接单、信用仅扣一次、通知失败回滚和旧接口并发写保护。模拟器真实 HTTP 用例也完成发布、重放、取消和审计查询，并验证业务 403 不会丢掉有效登录。

真实 MySQL 走通四业务发布，取消、并发接单与原完成确认，后端重启后重放结果相同。本轮真实模型仅调用一次，返回发布操作建议，确认它没有直接写任务。记录见 [数据库与模型联调](./evidence/07-mysql-and-ai-smoke.json)。

界面检查和截图见 [第五步证据汇总](./evidence/07-step5-summary.json)。测试中发现并修正“载入已选情境误触发未保存状态”和“执行成功后预览仍显示旧状态”；真实页面证据和接口结果共同复核，不能用构建成功替代交互验证。
