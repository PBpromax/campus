# 第三步：鸿蒙动态卡片与固定表单降级

日期：2026-10-24。延续四业务M1与第二步服务端草稿，不改数据库或生产API。

## 这一步实现什么

鸿蒙端增加可序列化的JSON卡片协议，由有限本地规则根据服务端草稿生成，再经过解码校验，交给ArkUI原生组件渲染。生成器、协议校验与页面操作分开；没有执行JSON中的代码、组件路径、网络地址或脚本。尚未接入模型、流式UI或真实任务发布。

| 业务 | 卡片分组 | 按需变化 |
| --- | --- | --- |
| 物品借用 | 规格与用途、使用归还时间、取还交接 | 缺少规格/时间/交接显示相应编辑器，配件和送达条件由后端情境规则决定 |
| 跑腿代办 | 代办内容与时间、交接与通知 | 指定点放置保存后增加具体放置点；静默与电话冲突显示调整提示 |
| 学习辅导 | 当前问题与讲解条件 | 初始只需当前问题上下文；保存基础/时间/语言等情境后再显示对应缺口 |
| 其他互助 | 目标资源范围、时间位置与沟通 | 按协助人数、授权条件及完成标准显示待补充内容 |

只显示当前缺失字段及已经填写的字段，其他可选条件通过“补充其他条件/使用完整表单”填写。条件变化先保存，后端重新校验后再生成新卡；不在输入尚未保存时假装完成约束判断。学习消息仍单独保存，不会被自动发布为任务，也没有伪造AI答疑。

## 协议与操作边界

实现文件：`harmony/entry/src/main/ets/ui/CardProtocol.ets`。渲染入口为`Needs.ets`中的`dynamicCard`。

顶层字段固定为：`version`、`source`、`sessionId`、`sessionRevision`、`category`、`draftRevision`、`cards`。

- 本版version=1、source=local_rules；不声称支持外部模型卡片输入。后续接模型需要新增受控入口，仍须复用校验边界。
- cards最多8张；每张只含id/kind/title/fields/message/actions；id唯一，未知属性被拒绝，JSON最多24000字符。
- 三类原生组件：fields（编辑器分组）、notice（冲突提示）、review（草稿核对）。字段组件仅text、number、datetime-local、select；字段键按四业务独立白名单校验，不能将借用字段放入学习卡。
- 三类操作：save、review、form，分别调用保存并重校验、核对草稿、切换完整表单。save仅允许在字段卡，review仅允许在核对卡；禁止publish、任意HTTP、JavaScript和WebView等指令。
- 每次点击重新检查会话ID、会话版本、类别和草稿版本。未保存字段/上下文、未选择本次业务、服务端缺失或冲突都会阻止核对。
- 草稿确认仍经真实后端核验，不产生原平台Demand，不代表对方授权。修改、补充消息与业务恢复沿用第二步确认失效规则。

## 降级与恢复

JSON损坏、版本过期、超限、未知组件/操作、非法字段等校验失败时，解码器返回空卡片和错误，页面显示完整表单。用户已输入的字段留在页面状态中；只切换呈现方式，不重置会话或发送发布操作。

用户也可以主动切换完整表单，补充未出现在卡片上的可选条件，再返回卡片。网络或409冲突沿用第二步保留输入与明确放弃后重载流程。固定表单核对也受后端规则及用户未保存输入检查约束。

## 手动验收步骤

1. 在模拟器启动Campus→“进入统一需求与草稿”→登录已有平台账号。
2. 选择物品借用，观察规格/时间/交接分组；填写规格并保存，检查草稿版本更新。
3. 选择跑腿，完整表单中填写“指定点放置”后保存，检查卡片要求具体放置点；用静默情境＋电话保存，检查冲突提示。
4. 选择学习，只输入当前知识点/表达式并保存，检查未要求报酬、地点和截止时间；补充时间紧张情境并保存，检查新增优先问题与可用时间。
5. 选择其他互助，补充目标、资源、标准，再检查情境对应缺口。
6. 在卡片输入尚未保存的内容，切到完整表单再返回，核对内容保留；保存后检查卡片更新；未保存字段或消息时不能确认。
7. 切换并恢复原业务，检查原草稿仍在而旧确认失效；确认按钮只核对当前草稿。

以上步骤是待执行的完整人工界面验收提纲，不是虚构的通过记录。构建、安装与测试命令沿用[harmony运行说明](../../harmony/README.md)。下一步接真实模型和流式协议，再完成可信工具闭环。
