# 第四步：DeepSeek流式对话与四业务草稿建议

日期：2026-10-24。本机后端8081＋API26鸿蒙模拟器，延续四业务基线。

## 实现结果

DeepSeek API Key仅在被Git忽略、权限600的`.env.deepseek.local`，由后端启动器读取。鸿蒙客户端只持有平台登录JWT，不持有模型Key。真实模型使用已验证的`deepseek-flash`非思考模式，官方`/chat/completions`流式接口；供应商重定向不自动跟随。

现在的操作路径：

> 表达目标/选择业务 → 发送给DeepSeek → 文字逐段出现 → AI提出字段建议 → 用户核对并选择采用/忽略 → 服务端更新草稿 → 规则生成最新卡片 → 核对草稿。

本步没有接通真实发布/接单/取消工具。AI的文字也不代表系统执行成功；界面和提示词均明确这一点。

## 四业务与个人上下文

- 用户未选类别或重新表达目标时，AI只可给分类候选，不能自动选择或写入领域字段。混合目标仍由用户明确选择一项，未知不默认OTHER。
- 当前已选业务只允许对应字段。模型接收当前业务草稿与最近最多20条相关消息、共用入口原话及字段目录，不发送账号密码、JWT或模型Key，也不把其他业务草稿作为当前上下文。
- 借用、跑腿、其他互助继续按第二步的规则检查缺失与冲突；模型不能确定库存或他人同意。
- 学习可直接答疑和连续追问，不要求报酬、地点和截止时间。用户消息与完整AI回复均持久化，重新登录/加载后可恢复已保存对话。
- AI只是提出建议，未采纳不修改领域字段。建议不是事实保证，仍须用户审核与纠正。

## 结构化建议与校验

提供一个受限的模型函数`propose_draft`，只能返回`fields`和`candidates`；服务端不会执行模型任意函数或代码。只接受本业务白名单中的字符串字段、合法分类和有限长度。`consent`、`deliveryConsent`授权字段禁止通过模型填写，仍由用户表单声明。

每条建议有随机token，绑定用户、会话、会话版本和类别，有效期5分钟。服务端设有256条待核对建议容量门槛、过期时清理；同一建议成功采用后删除，重启也失效。采用前再次检查所有权、版本、当前业务及待分类状态，再调用原领域编辑服务；不会绕过原有确认失效规则。用户有未保存输入时，客户端也阻止采用。

### 实际反例与修正

四业务真实调用中，OTHER输入只提到“两张桌子和三张海报”，没有说明人数；模型却提出`helperCount`字段。本次不把“模型返回JSON”当作语义正确。

新增人数证据检查：没有用户原话中的明确人数依据，也不是已有草稿人数时，移除人数建议并给出提示；其他合法字段仍可待核对。加入“物品数量不能成为协助人数”和“明确两位同学允许建议2人”两条回归测试。

这是针对实际反例的有限检查，不是完备的自然语言事实证明；否定、歧义、复杂数字及其他字段仍可能误读，必须保留人工核对，不能据此宣称模型零幻觉。首批真实联调记录保留了修正前的实际现象，没有将其改写为修正后的测试结果。

## 流式协议与中断恢复

新增登录接口：

| 接口 | 用途 |
| --- | --- |
| GET `/api/need-sessions/ai-status` | 只返回是否配置和供应商，不泄漏Key |
| POST `/{id}/ai-stream`（同前缀） | 正文`{revision,text}`，先保存用户消息，再流式回复 |
| POST `/{id}/ai-proposals/{token}/apply` | 正文`{revision}`，明确采用已核对的字段建议 |

SSE事件固定为：

| 事件 | 内容 |
| --- | --- |
| session | 服务端草稿/对话快照，包括保存用户输入及完整回复后的新版本 |
| text_delta | 自然语言片段；不传思考过程或原始工具参数作为用户回复 |
| proposal | 已过字段检查的待核对建议、候选、约束评估与提醒 |
| notice | 建议被拒绝等提示，不执行草稿写入 |
| failure | 上游/中断/并发变更错误提示；完整表单继续可用 |
| done | 完整响应结束标记；缺失该标记不能当作成功 |

客户端使用流式UTF-8解码，处理中文跨字节分包、CRLF及多事件同包，拒绝未知事件/损坏JSON/超大响应。提供“停止接收回复”；无自动重发、无无限重试。后端同时最多4条模型流、同用户最多1条；上游请求及响应时长/大小有界，超时和断开会关闭读取资源。

已经保存的用户输入和完整回复可以重新加载恢复。未完成回复不写入正式对话；重新加载会清除临时片段。当前未实现逐token断点续流或自动重试，避免把半截输出当作已完成建议或重复消耗API请求。停止接收不保证已在供应商处理的请求不计费。
