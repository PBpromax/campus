# 03 对话与卡片原型

源码与运行说明见 [prototype](./prototype/README.md)。这是一套Vue有限规则原型，不是鸿蒙客户端、ArkUI Schema Renderer或真实AI服务。JSON契约用于设计衔接，不能作为已完成M2的证据。

## 1. 交互流程

```mermaid
flowchart TD
  A[统一表达目标或选择四类业务] --> R{分类是否明确}
  R -->|未知或混合| Q[候选分类与用户选择]
  Q --> B[表达目标/载入设计样本]
  R -->|明确且用户选择| B
  B --> C{必要信息和约束是否明确}
  C -->|缺失或冲突| D[必要追问/结构化补充]
  D --> C
  C -->|学习普通交流| E[保留上下文并继续短消息]
  E --> F[用户标记解决]
  E --> G[主动准备发布]
  C -->|借用/跑腿/其他| H[领域约定卡]
  H --> G
  G --> I[补原系统发布字段]
  I --> J[当前版本确认卡]
  J --> K[模拟确认/模拟发布结果]
  H --> K
  J -->|修改| D
  D --> L[固定表单回退/模拟人工接管]
```

## 2. 二十组对话脚本

以下是设计脚本。规则原型可通过样本入口、输入与结构化补充验证关键行为，不承诺能自由理解所有自然语言。示例回答只展示澄清和线索延续，不提供真实数学或设备使用解答。

| 场景 | 用户表达 | 必要追问 | 用户补充及交互结果 |
| --- | --- | --- | --- |
| B01 | 展示要借转接器，不知道接口怎么选 | 电脑和投影是什么接口？未知能力如何核实？ | 补USB-C/HDMI要求；规格进入草稿，资源适配仍待核实 |
| B02 | 19点展示，得提前拿到 | 最晚拿到、结束使用、归还各是什么时间？ | 补具体时间；若拿到晚于使用则风险卡阻止确认 |
| B03 | 行动不方便，希望送到宿舍门厅 | 明确哪栋、哪个位置；出借方同意了吗？ | 选待协商；卡片保留请求性质。变为当面后重新确认接收位置 |
| B04 | 第一次用相机，需要说明 | 需要哪些配件和说明？限制需向谁核实？ | 补充充电器/存储卡请求；不虚构教程或已提供配件 |
| B05 | 借两天，归还时原地点可能不可用 | 完整日期、归还位置和硬期限是什么？ | 明确替代交接请求；超过已知期限须重新协商 |
| L01 | 导数定义也不懂，不知道从哪问 | 希望从极限还是定义开始？ | 选择从基础讲，先明确讲解起点 |
| L02 | 只有20分钟 | 最优先弄懂哪一步？ | 记录优先问题，缩小范围，不将20分钟变成预约时段 |
| L03 | 不方便见面，想发消息问 | 线上异步还是同步？ | 选择线上异步，不强迫线下位置 |
| L04 | derivative看不懂 | 中文、英文还是双语术语？ | 保留原术语与语言选择，不宣称已提供真实翻译 |
| L05 | 第二步到第三步怎么来的 | 只需贴出两步或相关题目 | 补x=-2→-x=2，再问负号；上下文保留，无预算表单 |

| R01 | 下不了楼，大件送门厅 | 重量、件数、搬运限制和接收点？ | 补限制，保留协作者能力待核实 |
| R02 | 上课别打电话 | 可交接窗口和通知方式？ | 选静默消息；选电话则提示冲突 |
| R03 | 新生不知道快递点 | 校区、站点或地标是什么？ | 补明确取件点；附近不能确认 |
| R04 | 英文表达取件需求 | 用哪种语言确认地点时间？ | 记录语言，不宣称已经真实翻译 |
| R05 | 指定地点放置 | 具体放哪里，如何通知与确认？ | 明确放置点和照片通知；改当面清空旧凭证约定 |
| O01 | 电脑连不上网 | 设备、系统、故障现象？ | 补资源条件、排查范围，修复结果不保证 |
| O02 | 活动需要几个人 | 人数、分工、组织方式？ | 明确一人协调或单人任务拆分；不虚构多人接单 |
| O03 | 线上帮查设置 | 用什么渠道、授权什么操作？ | 补渠道和完成标准，不默认远程控制授权 |
| O04 | 只有半小时整理资料 | 具体日期开始、优先范围？ | 补开始时间；逆序不能确认 |
| O05 | 泛泛地协助活动 | 做哪些事，怎样算完成？ | 明确范围和验收，帮忙/随便等标准不够 |

## 3. 卡片与控制

| 卡片/区域 | 内容 | 出现条件和允许动作 |
| --- | --- | --- |
| 借用规格与约定 | 用途、规格、数量、时间、取还位置、说明和协商 | BORROW；按情境补字段，用户修改 |
| 跑腿交接 | 取送窗口、交接方式、放置点、通知与凭证 | RUNNING；放置与当面两条路径，可修改重确认 |
| 其他协助 | 范围、资源、授权、时间、完成标准及多人组织 | OTHER；人数大于1增加组织决策，不把待授权当执行许可 |
| 业务选择 | 候选分类与原话 | 统一入口、跨业务或混合目标；用户选择后进入领域 |
| 保留草稿 | 原业务字段、消息与版本 | 跨业务切换后显示恢复；恢复旧确认失效 |
| 风险提示 | 地点含糊、日期非法、时间逆序、归还超期 | 冲突出现；确认禁用，要求选择或修改 |
| 问题线索摘要 | 当前表达式、知识点、卡住步骤 | STUDY普通交流；继续短消息、标记解决，无正式确认卡 |
| 发布确认 | title/description/category/expectedTime/reward/location及上下文 | 用户主动准备发布；用户补齐并核对 |
| 模拟结果 | 当前版本已确认，不产生真实业务ID | 必要信息完整，用户明确点击确认 |
| 固定表单回退 | 当前字段和相同规则 | 随时切换，保留草稿，不能绕过校验 |
| 模拟接管 | 当前上下文交接提示 | 用户主动选择；不发送真实客服请求 |

标题和描述可整理为派生草稿，来源标签明确；报酬、完成时间、服务位置不自动补值。派生标题和说明随领域字段更新，用户手写说明不会被覆盖。多人拆分显示候选请求列表；每项分工、报酬与授权仍需核对，M2实现部分失败与补偿。

支付、人员匹配、借用库存、预约和真实数学答疑均未实现；不展示可真实执行的预约入口。

## 4. 修改、撤销与结束

- 字段改变后增加草稿版本并清空旧确认；同值重复选择不破坏约定。
- 交接方式改变后重新确认接收位置和送达条件，不把新约定当旧授权。
- 撤销上次修改恢复字段，但仍需按新版本重新确认。
- 撤销本次草稿、标记解决、模拟接管结束当前会话；重置恢复设计样本或空白状态。
- 本地草稿撤销不是调用 `/api/demands/{id}/cancel`，不适用真实订单取消成功的说法。

## 5. 样本外输入与能力边界

支持键值式纠正，例如 `物品：相机；用途：拍校园活动`，字段标签或内部key都可识别；学习可直接贴含等号或箭头的两步表达式，之后继续短消息。某些短语可识别，如“改成送达”“从基础讲”“线上异步”。识别不了的信息通过结构化补充，不会声称已经理解。统一入口识别借用、学习、跑腿和代表性的其他互助关键词；候选要由用户选择。输入“帮我代取快递”会提出RUNNING，“电脑连不上校园网”会提出OTHER；未知输入保留未知，混合需求提出多个候选。

直接点击业务入口可载入设计样本；在分类待选择时点击业务入口即作用户选择，进入空白领域草稿而非预填样本。样本切换替换当前样本草稿；跨业务保留的草稿可恢复。新会话、重置或刷新清空保留草稿。

M1的有限规则不能替代模型理解、真人反馈和资源核验。需要持续试用后调整问题顺序和字段；这次没有编造满意度或学习效果。

## 6. M2衔接

保留BORROW/STUDY/RUNNING/OTHER场景和规则，再实现鸿蒙领域模型、白名单Renderer、流式协议、真实模型和可信工具。现有聊天用于任务参与方交流；发布前AI对话、借还结构化字段、幂等确认及普通人工工单仍需新增设计与实现。


### 四业务 M2 实施边界

M2统一需求入口须使用允许的四类枚举；模型只提出类别和字段候选，后端校验再更新草稿。未知类别返回可操作的澄清与手动选类，而不是接口报错结束流程。

实施顺序：通用鉴权/任务工具→四领域字段与持久化→统一会话/路由→四类卡片→发布/接单/凭证/确认/取消→故障与跨业务回归。跑腿预算不冒充真实支付；借用取借与归还需要明确领域阶段；OTHER多人拆分需要每项权限与幂等，部分失败可查询和处理；学习普通对话不强制任务化。

最终要覆盖四类真实流程，不能只把另外两类做成能点击但无法发布的入口。M1二十情境是M2回归种子；M2仍须验证真实模型理解和执行结果，不能用M1模拟结果替代。
