# ADR-002：ArkTS主客户端与仓颉只读状态组件

日期：2026-10-24。状态：本机双语言实现、构建和一致性验证通过；当前选择保留Java生产业务底座，用仓颉承担可选的只读投影组件。

## 为什么选这个组件

既有平台已用Java/MySQL实现信用、状态、确认、幂等与事务。客户端需要知道接单/取消预计改变什么状态，适合抽出TaskSnapshot＋TaskEvent的有限模型。它足以比较空值、枚举、错误表达与并发；请求不带用户自由文本、密码或模型Key，也不会因课堂语言实验重写原有事务。

仓颉实现已经由Java后端实际调用，鸿蒙增加“预览状态变化（不执行）”按钮；客户端在同一数据库快照上再运行ArkTS模型核对结果。当前LLM的function tools仍是propose_draft/suggest_action，这一步是AI原生应用调用确定性组件，未声称模型已自动注册、规划或调用第三个function tool。

## 同模型比较

| 维度 | ArkTS实现 | 仓颉实现 | 当前判断与证据 |
| --- | --- | --- | --- |
| 类型 | string enum、interface，JSON边界仍需运行时校验 | enum模式匹配、值类型struct；解析失败用异常 | 240行共同样本一致；格式正确不等于业务全部授权 |
| 数值 | 安全整数number | Int64 | 共同收窄到0—2^53−1，避免跨语言丢精度；上限拒绝自增 |
| 空与未知 | Map.get返回undefined，显式处理 | Option与穷尽match，未知枚举在解析时拒绝 | 编译器可提前发现部分错误，边界检查仍不可省 |
| 可变性 | 对象是引用；投影复制输入与回执，防止调用者篡改历史 | struct承载快照；共享class内集合由锁保护 | ArkTS有调用者改写返回对象的回归；仓颉去重结果在临界区内保存 |
| 并发 | 当前模型由单个UI事件循环拥有；Promise不等于多线程安全 | spawn worker、AtomicInt64发号、Mutex保护投影 | 仓颉24轮512事件竞争均仅一次推进；128同ID请求仅1次推进，其余重放 |
| 错误 | Error用于非法结构，Decision用于可预期冲突 | 异常用于解析/执行，Decision用于可预期冲突 | 两者区分坏输入、版本冲突、角色/状态不匹配；不自动重试 |
| 工具链 | 已有DevEco API26环境，适合原生ArkUI | 新增独立1.2.0 SDK，固定协议跨进程调用 | 两边实际构建/测试通过；仓颉运行库必须随部署提供 |

第一版仓颉spawn尝试捕获可变局部cursor，被编译器拒绝；改成let绑定的AtomicInt64。HashMap下标访问与Option读取也存在语义差异，先通过小型编译探针确认。没有将能编译等同于已经并发安全：去重和状态更新仍要由同一个锁保护。

## 并发实验如何解读

进程实验原始样本和P50见[02-cangjie-verification.json](./evidence/02-cangjie-verification.json)。SERIAL/PARALLEL各12轮，每轮512个不同事件争同一版本。两组都只有1个APPLIED、511个VERSION_CONFLICT，说明受保护状态的一致性；耗时包含进程启动。

这是非常短的临界区，四worker没有显示出可据此宣称的稳定提速。全局Mutex也会串行化独立任务。本轮价值是并发语义、明确冲突和可调用组件，不据此替换Java业务服务；若未来要提升吞吐，应先测真实负载，再考虑分任务分片、常驻服务、背压与隔离。没有对ArkTS事件循环和macOS仓颉进程做不公平的吞吐排名。

## 决策与后续代价

1. ArkTS保留主客户端与状态展示；当前Map对象不共享给TaskPool/Worker。未来若迁移后台worker，须使用消息传递或Sendable约束，而非把现有Map直接共享。
2. 仓颉保留可选只读组件；每次从数据库快照新建投影，进程退出即丢失。生产幂等仍用MySQL，不声称此投影能跨重启去重。
3. Java继续作为身份、业务和事务边界。角色、状态和版本由后端查询，模型/客户端不能把伪造身份传入组件作为授权。
4. 当前子进程启动及运行库是部署成本；仅在macOS arm64验证，不能直接把该二进制放到Linux云主机。M3部署步骤要在目标平台重新构建或使用兼容镜像。
5. 预览失败可跳过预览，真实执行检查照常。后续组件超时、持续故障与整体SLO必须一起评估；不能用本轮组件测试替代整个M3可靠性验收。
