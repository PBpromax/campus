# 第四步：可重复部署、健康检查与恢复

本轮把既有Java服务与仓颉组件部署到独立的本机Linux arm64容器中，验证新库启动、重启、故障回退及备份恢复。部署步骤是本项目安排，用来支撑课件第13页的部署决策及第14页“救得回”的运行证据；容器、Flyway和端口号不是教师指定实现。压测/SLO仍在第五步。

## 部署结构与版本

`本机HTTP 127.0.0.1:18082 → Java21后端/Agent/可信工具 → 项目内网MySQL8.0.46`

后端镜像内包含仓颉1.2.0 Linux组件和必要运行库；模型继续采用既有DeepSeek云API路线。隔离演练未挂真实模型Key，模型入口降级为表单/真人协商，付费调用0次。正常开发实例仍使用原8081入口，本轮新容器没有替换鸿蒙开发客户端连接。

## 健康与恢复语义

[Spring Boot 3.2健康分组](https://docs.spring.io/spring-boot/docs/3.2.0/reference/html/actuator.html#actuator.endpoints.kubernetes-probes)区分存活与就绪。本项目将db纳入readiness，不纳入liveness；不把可回退的DeepSeek和仓颉组件故障视为整个业务系统死亡。健康检查不会发送付费模型请求。

[Compose服务依赖](https://docs.docker.com/compose/how-tos/startup-order/)用于等待数据库健康，运行中是否可服务仍由HTTP探针观察。单个容器标为unhealthy不会自动把流量切走或保证自愈，不能把Compose依赖排序当高可用。当前只有单实例、单数据库。

默认优雅关闭50秒、容器停止65秒，模型请求45秒的上限仍保留；本轮验证空闲退出与持久化恢复，没有验证长流无损迁移、会话逐Token续传或任意故障下零丢失。

发布前要求声明数据库向后兼容，备份后再换镜像。失败自动回退只恢复应用，新增DDL不撤销；不兼容迁移不能套用这条回滚路径。A/B演练使用同一Jar、不同配置标记，证明发布脚本和数据保留，不证明任意旧业务代码均兼容新结构。

## 实际验证与修正

详见[部署演练原始结果](./evidence/04-deployment.json)。

1. 空库没有旧账号/任务，自动执行V1—V6，登录、会话消息、只读仓颉预览和可信取消可用；预览未改任务。
2. 数据库停止后存活200、就绪503，恢复后重新就绪。本次观察约5.3秒包含停止数据库开销，不当成SLO或稳定恢复时延。
3. 重启后原JWT和会话仍可用；成功执行的取消回执重放为SUCCEEDED、信用不重复扣减。
4. 故意启动即退出的候选被拒绝、旧应用恢复；健康配置B发布后显式回滚A，版本账本保留。
5. 备份恢复到第二个空库，7类关键表行数及HTTP中的会话/任务/回执一致；这是实际恢复验证，并非只检查SQL文件存在。
6. 仅在恢复副本中改坏V6校验值，Flyway阻止启动；finally恢复原值后重新健康。没有忽略校验或编辑已发布SQL使其通过。

首次容器启动发现仓颉SDK运行库目录为root专用权限，预览503；修正运行目录权限，并把普通用户运行协议纳入镜像构建，随后240样本及真实HTTP预览通过。测试过程中保留同一个合成账号/任务，没有清库重来。

新增Actuator后，首次后端回归遇到SSE响应头并发修改，之后连接池请求被阻塞；将Spring Security响应头改为在异步写流前写入，完整重跑283项通过。没有删断言或把失败日志改为成功。初次镜像下载超时后改用官方ECR镜像分发；Ubuntu依赖源调整为HTTPS main，修正一次源配置语法错误后构建完成。初始化脚本曾使用Path.open不支持的参数，修复后保留已生成凭据并补齐状态。
