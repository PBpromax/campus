# M3现场演示与变化挑战

建议演示约10—12分钟。主线是“说清需求 → 改变约束 → 重新确认 → 查看执行影响 → 展示可靠性证据”。不用逐页朗读全部文档。

## 演示前准备

1. 在仓库根目录运行只读预检：`python3 scripts/verify-m3-delivery.py --preflight`。它不登录、不发模型请求、不重建数据库；检查本机8081/18082、模拟器与组件/配置是否存在。
2. 开发服务未启动时：确认本项目3308数据库已运行，再执行`python3 scripts/dev-backend.py .env.m3-demo.local`。本机私有配置已保存，不能把临时环境文件或Key复制进提交材料。新机器按[开发说明](../../DEVELOPMENT.md)配置自己的私有值。
3. 模拟器未启动时，在DevEco启动`Campus_M2_Phone`。本机也可使用已安装工具：

```sh
/Applications/DevEco-Studio.app/Contents/tools/emulator/Emulator -start Campus_M2_Phone -instancePath /Users/pbpromax/.Huawei/Emulator/deployed -imageRoot /Users/pbpromax/Library/Huawei/Sdk
/Applications/DevEco-Studio.app/Contents/sdk/default/openharmony/toolchains/hdc -t 127.0.0.1:5555 rport tcp:8081 tcp:8081
```

4. 使用合成演示账号。私有账号夹具在本机被Git忽略的`deploy/private/classroom-demo/credentials.json`，自动排练可读取；不要把用户名/密码/token投屏或写进报告。
5. 打开[当前评审总览](./08-评审总览.md)、[第五步结果](./07-容量SLO与故障演练.md)及应用。当前UI为“对话 / 任务 / 消息 / 我的”；早期截图/脚本中的“可信操作”“预览状态变化”在新版分别位于任务页、“查看影响”。

预检不通过先修复对应环境。不要为了绿色状态关闭权限检查、清库或把真实模型悄悄替换成未标注的模拟器。

## 现场主线

| 时间 | 操作 | 给评审看什么 |
| --- | --- | --- |
| 0—1分钟 | 展示四业务首页和当前总览架构 | 在老师平台上接管升级；用户确认与模型候选分层 |
| 1—4分钟 | 借用需求，修改归还时间/地点 | 个性化约束进入卡片，规则发现冲突，修改使旧确认失效 |
| 4—6分钟 | 任务页“查看影响” | Java读真实快照，仓颉投影，ArkTS核对；预测不改变真实任务 |
| 6—9分钟 | 查看负载/故障原始样本，运行离线核验 | 52正常、6准入拒绝、48重放分别统计；HTTP200不等于成功 |
| 9—12分钟 | 展示部署恢复记录、预算和不足 | 解释模型/语言/部署选择，回答现场变化，诚实说明边界 |

### 场景一：借用任务与约束变化

从“＋ 新对话 → 物品借用”开始。网络和预算允许时可现场发送一次真实请求（会消耗一次API额度，不自动重试）：

> 我想借1个USB-C转HDMI转接器用于课堂展示。明天9点前在图书馆一楼服务台当面交接，9点半开始用，11点结束，12点在同一服务台归还。先整理需求，不发布。

核对模型提出的字段，点“保存到需求”。模型可能漏填或提取不准，按实际卡片补齐；不要把生成结果默认当事实。也可直接点“手动填写需求”，依次填写物品、用途、规格、数量、最晚拿到/开始使用/结束使用/归还时间、取还位置、交接方式。时间通过日期选择器设到未来，不能照抄旧截图日期。

现场变化：把归还改为当天10:00，保存。结束使用11:00与归还10:00冲突，界面应提示，不能继续有效发布。再改为12:30，归还地点改为“图书馆北门服务台”，保存并重新“核对需求，继续发布”。

填写标题、正数报酬、地点和未来完成时间，点“下一步，核对发布”。检查最终卡片的时间和位置。默认演示在此点“返回修改”，撤回本次操作，不发布任务；需要展示真实发布时，只能对明确的本地合成任务最终确认，并说明没有真实支付。

旧确认不得因修改后仍存在就继续执行；服务端会重新检查来源版本。本轮原生排练和截图见[串行排练](./evidence/06-review/borrow-ui-serial/review.json)。

### 场景二：仓颉只读状态预览

可用辅助脚本准备一条合成任务，读取已有两个账号，不注册或提权。文件存在时拒绝重新prepare；中断后沿用同一state执行ui或cleanup。下列私有state和输出目录需要使用新的名称，不能覆盖已完成的提交证据：

```sh
python3 scripts/review-m3-demo.py prepare --credentials deploy/private/classroom-demo/credentials.json --config .env.m3-demo.local --state /tmp/m3-demo1-private.json --output /tmp/m3-demo1-evidence
python3 scripts/review-m3-demo.py ui --credentials deploy/private/classroom-demo/credentials.json --config .env.m3-demo.local --state /tmp/m3-demo1-private.json --output /tmp/m3-demo1-evidence
```

脚本准备任务使用原任务创建API，明确是测试夹具，不说成AI自动发布。新版界面路径：helper账号 → 任务 → 找互助 → 相应测试任务的“了解并接单” → “查看影响”。页面说明“确认后……变为进行中”；真正任务仍应待接单、版本0、没有接单者。不要点“核对接单/确认接单”来证明只读。

排练完成后使用独立明确确认取消这条测试任务，保留审计：

```sh
python3 scripts/review-m3-demo.py cleanup --credentials deploy/private/classroom-demo/credentials.json --config .env.m3-demo.local --state /tmp/m3-demo1-private.json --output /tmp/m3-demo1-evidence
```

应在原平台30分钟取消窗口内完成。超过窗口按业务规则处理，不直接改数据库伪造清理。当前这次排练已在窗口内取消，[记录](./evidence/06-review/preview-review.json)中的预测和最终取消是两个独立操作。

### 场景三：证明能扛住、能恢复

在根目录运行：

```sh
python3 scripts/verify-capacity-evidence.py docs/M3/evidence/05-capacity
python3 scripts/verify-m3-delivery.py
```

打开第五步表格，选一条TIMEOUT、一条正文断流、一个工具重放结果，对照原始JSONL/账本/审计。说明5秒实验截止与45秒默认模型截止的区别，以及“HTTP200但没有done”为什么不算成功。

如评审要求现场重新注入故障，按[容量实验复现说明](./evidence/05-capacity/README.md)使用新的受限项目名与输出目录。它有独立空库、假Key和内部网络，不会给真实DeepSeek压测；不能在8081或18082上直接启动故障注入。首次镜像/工具构建时间不包含在10分钟演示内，缓存和环境须提前检查。

第四步展示备份恢复/校验失败/回滚的实际证据即可。`restart-fault`包含取消副作用，不对已取消的旧任务盲目重跑。现场云部署不在本版本范围内。

## 现场变化挑战与可接受结果

| 评审提出变化 | 应观察/解释的行为 |
| --- | --- |
| “我只想问某一步，别让我发布” | 学习对话直接交流；发布字段按操作需要出现 |
| “把归还改到使用结束之前” | 保存后提示冲突，修改后旧确认失效 |
| “不确认，直接替我发出去” | 模型只能建议；系统要求有效版本与用户明确确认 |
| “同一按钮点十次会怎样” | 同一个有效回执重放返回原结果；48次实测只有一次副作用；新请求键不能绕过同草稿已发布约束 |
| “模型慢、断线或额度用完怎么办” | 保留已保存上下文，取消/重新载入，使用规则表单；没有自动付费重试 |
| “仓颉没启动呢” | 只读预览失败，真实工具仍按原权限/确认执行；不让缺少可选预览绕过校验 |
| “为什么4路还会拒绝别人” | 并发上限和背压策略；不排队；计入拒绝率，后续按预算/负载调整 |
| “这就是云端高可用了吗” | 当前本机单实例，做过故障/恢复；公网、跨节点和长期SLO未验证 |

## 结束核对

确认没有遗留正在运行的故障注入或额外压测容器。合成预览任务已清理为CANCELLED，草稿和历史审计保留；不删除用户数据或备份。返回“对话”的新首页，保留原演示服务。按实际情况记录老师反馈，不填写预设的满意度或验收通过结论。
