## 1. 课程最终要完成什么

将 CampusHub 1.0 的固定功能平台升级为面向个人特殊情境的校园智能体（第 2—4 页）。同一个目标应能根据用户的时间、地点、能力、语言、隐私和合作偏好，产生不同的澄清问题、交互卡片和执行流程。

最终闭环：自然语言表达目标 → 澄清缺失约束 → 生成结构化卡片 → 用户修改和确认 → 受控工具执行真实业务 → 服务端保存状态与审计 → 收集授权反馈 → 用评测证明下一版变好。

确定性底座负责业务规则与安全；模型提出候选行动；鸿蒙客户端渲染经过校验的声明式 UI。任务卡片可以到期失效，订单事实、授权与审计记录须保留（第 3、8、9、12 页）。

同一组白名单组件可以组合成不同流程，不要求为每种用户另建固定页面。重点是特殊约束确实改变澄清、UI 和工具参数。

### 4.2 业务本体落地

建议在原 User/Requirement/Order/Evaluation/Notification 模型外增加：

- `Goal`：用户希望达成的目标，例如本次代取三个快递。
- `TaskContext/Constraint`：时间窗口、地点、件数、语言、隐私、报酬和合作偏好；区分硬约束与可放宽偏好。
- `Resource/MatchCandidate`：取件点、公共交接点、服务方、可用时间、历史合作事实。
- `Authorization`：谁授权哪个操作、哪些参数/资源、何时过期、是否撤回。
- `AgentTask`：澄清中、等待确认、执行中、完成、失败、已取消等编排状态；它与需求/订单状态分别保存。

规则至少覆盖：不可接自己的需求；同一需求最多有一个有效接单；缺少必要信息不能发布；精确位置只给被授权对象；评价只能发生在完成订单的参与者之间；信用变化由确定规则执行；用户未确认不可产生发布、接单、取消等副作用。

### 4.3 M1 验收建议

五组脚本都能演示：输入 → 明确缺失字段 → 用户纠正 → 不同卡片/流程 → 修改或撤销。原型可以使用测试工具，但需标明模拟；从 W2 起就应产生可运行原型，并逐步接到真实后端，不能整个前半学期只做文档。

## 5. M2：在鸿蒙端真正跑通业务

### 5.1 必须实现的模块

1. **ArkTS/ArkUI Stage 客户端**：登录、对话、任务详情、固定发布表单、订单操作、错误/降级和人工接管入口。Vue 可保留作后台/调试与 Web 回退；只有 Vue 页面不能满足鸿蒙客户端要求。
2. **领域模型和状态机**：Task、Requirement、Order、Authorization、UiSchema；迁移由服务端验证，客户端不能自行宣布完成。
3. **Schema Renderer**：建议先支持文本、时间/地点字段、选项、确认卡、方案比较卡、进度卡；校验版本、字段类型、组件白名单、权限和 Action 范围，兼顾无障碍、多设备适配。
4. **流式协议**：明确处理 `assistant.delta`、`ui.schema`、`tool.pending`、`tool.result`、`task.state`；建议补充 eventId、taskId、traceId、sequence、version，以支持消息去重和断线恢复。SSE 或 WebSocket 选一种并解释选型。
5. **可信工具**：对现有 REST API 建立工具包装；只读工具和副作用工具分开。副作用必须由用户确认并经服务端鉴权、状态校验、参数校验、幂等和审计。
6. **撤销与降级**：未执行的候选操作可直接撤回；已执行操作按真实业务取消/补偿规则处理。模型故障、错误 Schema 或断线时可使用固定表单继续同一任务；人工接管必须能查看任务并处理，不能只有一个按钮。

模型只能输出声明式 Schema，不能在线执行模型生成的 ArkTS、JavaScript 或 SQL（第 8 页）。后端现有人工编写的参数化 SQL 属于业务实现，和模型生成并执行 SQL 是不同概念。

### 5.2 建议的工具契约

| 工具（建议命名） | 对接现有代码/新增能力 | 是否有副作用 |
| --- | --- | --- |
| `requirements.search/get` | 复用需求列表/详情，增加受控过滤与位置脱敏 | 否；仍须鉴权与对象/字段权限 |
| `matches.suggest` | 新增时间、地点、信用、合作历史匹配；只返回允许展示的候选 | 否 |
| `requirements.publish` | 包装现有发布，支持结构化约束与确认凭证 | 是 |
| `orders.accept` | 包装现有接单，补齐幂等、状态与并发校验 | 是 |
| `orders.get/complete/cancel` | 复用详情，新建完成与取消迁移 | 后两项是 |
| `locations.authorize` | 新增精确地点分级披露，授权与撤回 | 是 |
| `preferences.update/revoke` | 新增个人偏好管理，推测转声明须用户同意 | 是 |

确认凭证应绑定用户、工具、资源、具体参数摘要及有效期；确认后修改时间/位置/报酬要重新确认。幂等键绑定一次业务意图，重试返回原结果。客户端“确认按钮”本身不能替代后端验证。

### 5.3 补齐原业务闭环

沿用原订单状态：`IN_PROGRESS → TO_CONFIRM → COMPLETED`，明确由接单者提交完成、发布者验收；按规则进入 `CANCELED`。需求表随订单原子更新。新增转移表、参与者权限、完成/取消原因、重复请求处理、通知和审计。

取消后是否重发、何时允许取消、管理员下架如何处理进行中的订单，应先形成业务决定。旧表 `uk_req_id` 保证一个需求只有一个订单；若允许取消后重新接单，要先调整订单历史与有效订单约束，不能直接删掉唯一索引。

### 5.4 M2 现场通过条件

鸿蒙设备/模拟器现场输入一条需求 → AI 追问 → 渲染不同卡片 → 用户修改并确认 → 调用真实业务工具 → 数据库产生可查的需求/订单 → 展示服务端状态。再展示未确认不执行、重复确认不重复创建、非法 Schema 被拒绝、断线恢复与固定页面降级。

## 6. M3：能调用、扛得住、救得回

### 6.1 W8—W9 双语言与仓颉组件

- 同一 Task/Constraint/状态迁移模型分别用 ArkTS、仓颉实现；比较类型约束、错误处理、可读性和工具链，形成语言选型 ADR。
- 推荐仓颉实现小型事件校验/处理服务，或受控匹配计算服务；实际接入 Agent/工具流程，展示并发安全与错误语义，用测试或性能数据说明价值。
- 保留 Spring Boot 业务服务；课件要求仓颉小型组件，没有要求将整个后端改写为仓颉，也没有要求必须拆成复杂微服务。

### 6.2 W10—W11 智能体和模型部署

推荐结构：鸿蒙客户端 → Agent Orchestrator → Model Gateway / 业务本体与规则检索 → Tool Gateway → Spring Boot 业务服务与仓颉组件 → MySQL/Redis。

Agent 负责意图、澄清、计划、候选卡片和工具参数；Model Gateway 负责模型/Prompt/Context 版本、路由、配额、缓存、超时、重试、熔断和成本；Tool Gateway 负责确定性权限、确认、状态、幂等和审计。

本体与规则先做结构化可查询资产；如果使用 RAG，返回规则依据和版本，不将聊天记录当作权威规则。课件没有规定必须采购向量数据库。

提交 LLM 部署 ADR、模型路由策略和成本预算（第 13 页），解释：

- 云端、私有或端云混合为何适合我们的场景；哪些数据可以发送到哪里。
- 精确地址、取件凭证、身份信息如何最小化与脱敏；模型输入不能直接透传整个数据库。
- 单次任务输入/输出 Token、模型调用次数、费用估算与实测；单用户额度与峰值预算。
- 超时如何重试/换模型/回退规则；执行业务前后故障如何恢复，避免模型重试重复调用写工具。

| SLO | 团队定义首片段延迟、任务完成成功率、工具成功率、恢复时间与重复写入约束 | SLO 定义、观测口径、测量窗口和实测达成情况；课件未给统一阈值 |
| 模型超时 | 注入超时，切换备用路径或固定表单，继续原任务 | 故障步骤、trace、前后状态、恢复与成本记录 |
| 工具重复调用 | 相同幂等键重放发布/接单，业务只发生一次 | 请求/响应、审计与数据库断言 |
| 流连接中断 | 卡片或工具进度中途断网，重连恢复业务事实 | 事件重放与去重证据、任务一致性结果 |

端到端 trace 串起客户端、Agent、模型调用、工具与业务事件；日志不泄露隐私。M3 不能只交架构图，三类故障必须实际演练（第 14 页）。

## 7. M4：数据与评测证明系统变好

### 7.1 W13—W14 事件和个人记忆

事件至少覆盖目标表达、意图假设、澄清、用户纠正、Schema 生成/拒绝/渲染/操作、工具请求、确认、成功/失败/补偿、任务完成/放弃/降级/人工接管（第 16 页）。

建议统一事件字段：eventId、userId 的受控/匿名标识、taskId、traceId、eventType、occurredAt、outcome、modelVersion、ontologyVersion、promptVersion、schemaVersion、toolVersion。事件中的结构化摘要与受控原始数据分层存储，避免记录完整敏感 Prompt。

偏好须区分：

- **声明偏好**：用户主动声明“优先历史合作者”；可查看、修改和撤回。
- **推测偏好**：系统推测，明确标识；未经确认不得固化为人格标签。
- **临时上下文**：本次“脚受伤”、取件时间或临时位置；任务结束/到期删除或匿名化，不直接写进长期画像。

交付数据目录、字段字典、质量规则、权限矩阵和血缘。把每项连接到真实用途，例如“澄清纠正事件 → 缺失字段统计 → 本体/追问策略修订 → 新版评测”。

### 7.2 W15—W16 至少 40 条固定样本

建议五组各 8 条，共 40 条；可以扩充，分类和配额不是教师固定要求：

| 样本组 | 建议数量 | 覆盖点 |
| --- | --- | --- |
| 正常需求 | 8 | 单件/多件、时间地点清晰、合法报酬、正常发布与完成 |
| 模糊或缺信息 | 8 | 不明确校区、无时间、地点歧义、约束冲突、用户纠正 |
| 偏好与特殊情境 | 8 | 五类 M1 情境及组合、隐私披露、熟人不可用 |
| 攻击与越权 | 8 | 提示注入、读取他人订单、危险 Action、未经确认执行、隐私诱导 |
| Schema/工具/模型故障 | 8 | 非法组件、字段类型错、模型超时、工具失败、重复消息、断线恢复 |

每条样本包含 ID、输入、上下文、允许/禁止动作、应澄清字段、预期 Schema/状态、判断方法和版本。实际评测意图、澄清、Schema、工具选择、安全、延迟和成本；“能聊天”不能代替这些指标。人工评分与机器判定分开说明。

### 7.3 一个可复现的数据飞轮实验

建议实验问题：**依据授权事件中反复出现的时间/地点纠正，更新追问策略和动态确认卡，能否减少修改与误操作？**

1. 冻结任务集和旧策略：基线使用纯文本澄清/确认，保存版本与运行参数。
2. 收集真实、经授权的纠正/放弃/失败事件，分析高频缺失约束；不得编造用户数据。
3. 据此更新本体字段、澄清规则与时间/地点/方案卡；固定模型版本等可控变量。
4. 对同一任务集或随机/交叉分配的用户试用比较完成时间、修改率、误操作与满意度；说明分配方法、样本量和偏差。
5. 保存原始数据、分析脚本、复现步骤和版本差异，报告改进、无改进或退化均可，但结果须真实。

固定 40 条样本主要用于能力与安全回归；满意度等用户体验指标需要真实参与者反馈，不能直接从自动评测推导。

### 7.4 W17 红队与 W18 发布答辩

红队覆盖提示注入、越权、伪造按钮/危险 Action、重复订单、非法状态、未确认执行、信用误判、模型/网络故障和隐私泄露。每项记录攻击输入、实际结果、风险、修复和复测，纳入永久回归（第 19 页）。

最终现场需求不能靠写死脚本应付。可用第 25 页例子做准备练习：脚受伤、三个快递、不公开宿舍号、请喝咖啡、希望长期联系同一人。落地需组合件数清单、临时能力约束、隐私位置授权、非现金报酬与长期偏好候选；应对陌生组合继续澄清与处理，而不是命中某个关键词。

发布产物建议包括：鸿蒙构建包、业务/AI/仓颉可运行服务、数据库迁移与测试数据、环境变量说明、安装/启动/恢复手册、评测/实验/红队报告和已知限制。个人答辩需用真实 commit、设计记录和验证记录解释自己的贡献，现场定位或修改问题。

## 9. 建议的模块与开发顺序

优先完成一个可验证的取快递闭环；现有学习辅导、二手交易、活动组队保留原能力，待主线通过后再泛化。老师没有要求以新增分类数或页面数取胜（第 22 页）。

建议目录（尚未创建工程）：

```text
campus/
  backend/                 # 现有 Spring Boot 稳定业务；扩展状态、授权、工具、事件
  frontend/                # 现有 Vue 固定页面、调试与管理入口
  harmony/                 # 新增 ArkTS/ArkUI Stage 主客户端
  agent/                   # 编排与模型网关；技术栈在 ADR 中确定
  cangjie-service/          # 新增小型并发事件/工具服务
  contracts/               # UI Schema、流式消息、工具与本体版本
  evals/                   # 40+ 固定样本、评测与红队回归
  experiments/             # 真实数据飞轮实验及复现
  docs/AI-Native/           # 本学期路线、评审与证据
```

执行顺序：验证旧系统 → 补订单完成/取消和通知 → M1 特殊需求与本体原型 → 鸿蒙 Renderer/协议/工具闭环 → 仓颉与 Agent/部署 → 容量和故障 → 治理/评测/实验/红队/发布。M1 原型与底座补齐可穿插进行，别等旧系统所有扩展做完才开始新课程主线。

后续数据建模至少考虑 Task、结构化约束、偏好及撤回、授权、工具执行/幂等、审计与业务事件。具体表拆分在设计时决定；“请喝咖啡”建议建模成非现金报酬约定，不伪装成已实现支付结算。
